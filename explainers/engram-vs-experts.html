Why the Engram table can live on NVMe but the routed experts can't

DeepSeek-V4.1-Flash on one DGX Spark (128 GB). Its two Engram layers (1 and 14) hold a 183 GiB phrase-memory table; its routed experts are ~195 GiB at 3 bits. Neither fits in memory with the rest. Five animated scenes show why one of them can sit on a ~4 GB/s SSD at almost no cost and the other cannot.

Use case 2 · The same token, now through the experts

Each MoE layer's router scores 384 experts from the hidden state and picks 6. That hidden state only exists once the token has gone through every layer before it, so the read can't start early. Each picked expert is a whole matrix (~13 MB at 3 bpw) and all of it is multiplied.

Use case 3 · Decoding one token: who waits for whom

Engram rows are known the moment a token is sampled, so their reads start immediately and overlap with compute. Layer 14's lookup even has 13 layers of work to hide behind. Expert reads can only start when the token reaches that layer's router, so the GPU sits idle while they arrive.

Use case 4 · Reading a long document (prefill, 4,096-token chunk)

A prompt is processed thousands of tokens at a time. Every token adds its own 48 small Engram rows, but together the tokens pick nearly every expert in every layer, so the whole expert set would have to be read for each chunk.

Use case 5 · Coding and everyday text: hot phrases stay in RAM

N-grams follow a long-tail distribution: in the, of the, import numpy as, def __init__(self come up constantly. The OS page cache keeps their rows in spare RAM, so most lookups never reach the SSD. Rare phrases cost one small read.

Rule of thumb: anything you can look up and predict ahead of time (Engram tables, Qwen3.8-Flash-Next's n-gram embedding, Gemma's per-layer embeddings) can live on SSD. Anything you must multiply in full and only learn about at the last moment (MoE experts) needs to be in memory to be fast.
